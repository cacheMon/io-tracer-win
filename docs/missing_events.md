# Investigation of Missing File I/O Events in the Trace Collection System

## Background

One of the expected properties of the tracing system is its ability to capture file I/O activity generated by user applications. During validation, an inconsistency was observed: a simple Python workload that repeatedly performs file reads generated only a small number of trace entries, despite the tracer being configured specifically to monitor Python processes and file read operations.

This behavior raises concerns regarding event loss, buffering issues, or limitations in the tracer's filtering logic.

---

# Initial Observations

To understand whether file-related events exhibit temporal behavior, several long-running user processes were examined.

## User-Level Process Analysis

### Microsoft Edge (`msedge`)

* Exhibits a large spike of failed filename resolutions at startup.
* The failure rate does not converge to zero over time.
* Suggests that filename resolution failures continue throughout the browser's lifetime.

### LineMediaPlayer

* Failed filename resolutions do not appear to converge toward any stable value.
* Behavior is highly variable.

### Logman

* Generates events too sparsely for meaningful analysis.

### Windows Defender (`MsMpEng`)

* Displays a decreasing trend in failed filename resolutions.
* Indicates that some filename information may become available after handles have been observed for a period of time.

One possible explanation is that handles are not being reopened frequently, allowing the tracer to gradually learn and resolve more file objects over time.

---

# Controlled Experiment

To isolate the issue, a simple Python workload was developed.

## Workload

The script performs repeated random reads on a file.

Tracer configuration:

* Process filter: Python only
* Operation filter: File read operations
* Goal: Verify whether file reads are consistently captured

---

## Experiment 1: Python Script Started Before Tracing

Procedure:

1. Start the Python script.
2. Start the tracer.
3. Allow tracing to continue.
4. Restart the Python script while tracing remains active.

### Results

Observed events:

* Only `query_info` operations were captured.
* A small number of `read` operations were observed.
* Captured events contained empty filenames.

After restarting the Python process:

* Empty filename entries continued to appear.
* No improvement in filename resolution was observed.

### Interpretation

This suggests that filename resolution is not simply a matter of allowing more time for handle tracking to stabilize.

---

## Experiment 2: Python Script Started After Tracing

Procedure:

1. Start the tracer.
2. Wait until tracing is active.
3. Launch the Python workload.

### Results

Unexpectedly:

* No Python trace entries were observed.
* The workload was actively reading files.
* The tracer remained operational.

### Interpretation

This result is inconsistent with Experiment 1, where at least some Python events were captured.

If filtering and process matching are functioning correctly, Python read operations should have appeared regardless of launch order.

---

# Potential Causes

## Event Loss

Current evidence suggests the possibility of event loss.

Supporting observations:

* The workload generates significantly more read operations than are observed.
* In some runs, only two trace entries appear despite continuous file activity.
* In other runs, no Python events appear at all.
* The discrepancy is also visible when comparing the application's Debug.WriteLine output with the generated trace output. The debug logs indicate that the workload continues to perform file read operations, while the tracer records only a small subset of the expected events.

If event loss is occurring, then traces generated after the tracer starts may be dropped before reaching user space.

---

## Buffer Saturation

The tracing system currently relies on the built-in event buffer.

Potential failure scenario:

1. Kernel events are produced faster than they are consumed.
2. Buffers become full.
3. Events are dropped during flushing.
4. Python file I/O events are lost before processing.

This would explain:

* Missing trace entries.
* Inconsistent visibility of Python events.
* Different outcomes across repeated executions.

---

# Additional Experiment

A simplified experiment was conducted.

## Setup

* Listen only for `Read` operations.
* Restrict monitoring to Python processes.
* Start the Python script before tracing begins.
* Allow the workload to continue running.
* Restart the Python script approximately six minutes later.

## Observation

Before the Python process was restarted:

* Python trace entries were present.

After the Python process was restarted:

* Trace behavior became inconsistent.
* The expected volume of Python read events was not observed.

This suggests that process lifetime or process reattachment may play a role in the issue.

---

# Working Hypothesis

The most likely explanation is currently a combination of buffering and event delivery problems.

Evidence supporting this hypothesis includes:

1. The tracer captures substantially fewer events than expected.
2. Python events occasionally disappear entirely.
3. Results vary between repeated executions.
4. The workload is known to generate continuous read activity.
5. Empty filename entries indicate that event processing may be occurring before associated metadata is available.

However, the current evidence is insufficient to conclusively distinguish between:

* Event loss
* Buffer saturation

---

# Measurement Plan (ETW + TraceEvent Backend)

## Phase 0: Establish Baselines (CRITICAL — Do First)

Before running any experiments, measure these unknowns:

### Baseline 1: Python Workload Event Generation Rate
- **What**: How many file read operations/sec does the Python script generate?
- **How**: Instrument the Python script to log every read operation with timestamp
- **Output**: Events/sec (e.g., "1000 reads/sec" or "10 reads/sec")
- **Why**: Without knowing expected rate, can't detect loss

### Baseline 2: WriterManager Disk Write Throughput
- **What**: How fast does WriterManager write events to disk?
- **How**: Measure file size change over time while tracing
  - Option A: Monitor the output directory size growth (bytes/sec)
  - Option B: Add logging to WriterManager when flushing to disk (events written/sec)
- **Output**: MB/sec or events/sec to disk
- **Why**: If disk write rate < event arrival rate, disk is the bottleneck

#### Using Options A and B Together (Sanity Check)

**Option B** (instrumentation) gives you precise flush details:
- "At 10:00:00, flushed 1,000 events (50 KB)"
- "At 10:00:02, flushed 1,000 events (50 KB)"
- "At 10:00:04, flushed 1,000 events (50 KB)"
- → Calculated throughput: 150 KB / 4 seconds = **37.5 KB/sec**

**Option A** (external monitoring) measures actual disk growth:
- "Output directory was 100 MB at 10:00:00"
- "Output directory was 100.15 MB at 10:00:04"
- → Measured throughput: 150 KB / 4 seconds = **37.5 KB/sec**

**If they match** ✅: Your Option B instrumentation is accurate; use it going forward.

**If they don't match** ⚠️: Something is wrong:
- Option B logging may be missing flushes or miscounting bytes
- Option A polling interval may be too coarse (catching partial writes)
- Data may be written elsewhere you're not logging
- Data may be lost between flush and actual disk write

**Implementation order**: Start with Option B (add logging to WriterManager), then run Option A (directory monitor) in parallel to validate.

### Baseline 3: ETW Buffer Stats at Rest
- **What**: Current ETW session buffer configuration
- **How**: `logman query "IOTracer" -ets` (run while NOT tracing)
- **Output**: Buffer count, buffer size, event loss state
- **Why**: Know the starting point before adding load

## Phase 1: Load Test + Measurement (All Events)

**Key change**: Listen to **all event types** (not just Python reads). This is necessary to detect buffer saturation, which is system-wide.

### Setup
1. Enable all kernel providers in tracer (FileIO, DiskIO, Process, Network, Memory, etc.)
2. Start tracer
3. Verify ETW session is active: `logman query "IOTracer" -ets`
4. Launch Python workload at a *known* rate (e.g., 10 reads/sec, 100 reads/sec, etc.)
5. Let it run for 2-3 minutes at constant load

### Data Collection (Run Every 30 Seconds)

**ETW Buffer Health:**
```
logman query "IOTracer" -ets
```

What to capture and interpret:

| Metric | Meaning | What to Watch |
|---|---|---|
| `Buffers Lost` | ETW kernel buffer drops (indicator of overflow) | Should stay at 0 throughout test. If increases → buffer saturation confirmed |
| `Buffers Written` | Cumulative buffers flushed to disk | Should increase steadily. If stalls → no events flowing |
| `Buffer Size` | Total buffer capacity in MB | Compare against actual events/sec to estimate headroom |

**How to monitor:**
- **Baseline (before load)**: Run once, note `Buffers Lost` and `Buffers Written`
- **During load (every 30 sec)**: Run again, check if `Buffers Lost` increased (stays 0 is good)
- **After test**: Final query to see peak `Buffers Written` and whether any `Buffers Lost` occurred

**Note:** `logman query` does not show real-time occupancy %. If `Buffers Lost` stays 0, the buffer likely never saturated. If `Buffers Lost` > 0, it confirms kernel-level overflow.

**Disk Write Throughput:**
- Monitor output directory size growth (bytes/sec)
- Or: count total events written to trace per 30 seconds

**Python Workload Rate:**
- Verify Python logs show steady read rate (e.g., "100 reads/sec")

### Stop & Analyze

Calculate these three metrics:

1. **Expected Total Events**
   - Python reads: (Baseline 1) × (runtime seconds)
   - System events: rough estimate from previous traces (or measure separately)
   - Total expected: Python + system

2. **Actual Events Captured**
   - Count in trace file (filter by event type if tools allow)

3. **ETW Buffer State During Test**
   - Peak buffer occupancy %
   - Events lost (from logman output)
   - Did buffer reach 100%?

### The Correlation (Goal B)

Now answer:

**If ETW buffer occupancy peaked at ~100% AND events were lost:**
- Hypothesis: ETW kernel buffer saturation is the cause
- Next: Try increasing buffer size

**If ETW buffer occupancy stayed low BUT events still lost AND WriterManager disk rate << event arrival rate:**
- Hypothesis: WriterManager can't keep up (disk I/O or encoding bottleneck)
- Next: Profile WriterManager, increase output buffering

**If ETW buffer occupancy low, disk rate sufficient, but Python reads still missing:**
- Hypothesis: Loss is mid-pipeline (handler or queue logic)
- Next: Add event counting in `fsHandler` to see where loss occurs

## Phase 2: Identify the Bottleneck

Depending on Phase 1 results:

| Observation | Likely Cause | Next Step |
|---|---|---|
| ETW buffer occupancy ~100%, events lost > 0 | ETW kernel buffer saturation | Increase ETW buffer size (requires `logman` config) |
| ETW buffer occupancy low, but disk write rate << event rate | WriterManager falling behind | Profile WriterManager, check for I/O contention |
| ETW buffer occupancy low, disk write rate ≈ event rate, but events still missing | Loss between ETW→handler→disk | Add event counting in `fsHandler.OnRead()` to measure mid-pipeline |
| No loss detected at baseline rate, but loss at 10× rate | Capacity limit found — measure the cliff | Binary search to find exact saturation point |
